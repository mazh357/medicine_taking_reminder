# 长期用药助手｜药物基线照片闭集识别方案

> 本文冻结未来视觉实现边界，不声明当前 APK 已具备药物类别识别能力。当前 `OnDeviceVisionProvider` 和 `RemoteVisionProvider` 均必须报告不可用；人工拍照、逐药确认和库存主链不能依赖视觉。若本文与离线 MVP、数据契约或模型卡冲突，以更严格的安全边界为准。

## 1. 决策摘要

1. 视觉不是开放式识药：候选集合只包含当前服药任务中、由用户手工建立且拥有 active 外观基线的药物。
2. 逐药拍摄先行。药物类别来自当前拍摄药项上下文，模型只做画质、物体数和基线差异。
3. 整组拍摄后行。模型只能输出“根据你的基线建议分组”，每个对象必须允许人工改选或标记无法分组。
4. 计划数量不得作为检测或分组先验；检测数、候选分组、计划量和实际服用量必须保持独立。
5. 当前纯背景轮廓算法只保留为受控背景计数方案，不承担类别匹配。
6. 正式候选采用原生 LiteRT/TFLite 双工件：检测/质量模型与外观嵌入模型；模型、阈值和预处理随签名 APK 发布。
7. 任一视觉能力未达到门槛时关闭该能力，照片留存和人工确认继续；不得回退到联网模型。

## 2. 允许与禁止的任务

### 2.1 允许

- 对已加密保存的服药照片做离线画质门控。
- 统计完整可见且可分离的药片样物体总数。
- 在当前任务的本机基线集合内生成对象级候选药物 ID。
- 将候选按用户手工录入的药名聚合为待核对分组。
- 比较本次对象与其 active 基线，输出 `suspected_change`、`unable` 或仅内部使用的 `no_anomaly_signal`。
- 保存模型版本、原因码、耗时和对象框作为可追溯观察。

### 2.2 禁止

- 从任意图片推断药名、成分、厂家、批次、真伪、处方或疾病。
- 搜索当前任务之外的药物、外部药品图库或互联网。
- 把候选结果写成“识别正确”“药物正确”“剂量正确”或“可以服用”。
- 用计划数量补齐漏检对象、强制匹配类别或修正模型计数。
- 将结果写入 `confirmed_consumption_quantity`、服药状态、处方或库存。
- 自动确认服药、扣减库存、更新外观基线或删除旧基线。
- 上传照片、嵌入、药名或观察结果；当前版本不发起任何视觉网络请求。

## 3. 基线采集与版本管理

### 3.1 建立基线

- 用户先从已手工建立的药物记录中选择药物，模型不得填写药名。
- 每个外观版本要求单个完整物体的正面、背面各一张；外观对称也拍摄两次。
- 使用后置摄像头、纯色哑光背景、无遮挡、无包装、无手部遮挡；每张只允许一个物体。
- 激活前检查解码、单物体、触边、背景噪声、明暗、清晰度和反光。
- 质量不合格的照片可以加密保存，但版本只能为 `draft` 或 `manual_only`。
- 半片、破损片和透明胶囊只允许 `manual_only`，不得建立受支持基线。

### 3.2 更新与删除

- 每种药只有一个 active 外观版本。
- 用户显式创建新版本，并选择 `new_package_or_batch | appearance_changed | correction`；旧版本追加为 `superseded`，不得覆盖。
- 服药过程照片或疑似变化照片不能自动成为基线，避免错误样本自我强化。
- 同一种药新旧外观同时使用期间强制 `manual_only`。
- 删除 active 基线照片后立即关闭该药的外观比较，历史服药事实、库存和观察不变。
- 模型 manifest 变化后，旧嵌入不得直接复用；在原生侧重新生成并以新 manifest 版本追加。

## 4. 逐药与整组流程

### 4.1 第一阶段：逐药

1. 拍照页面已绑定一个任务药项，类别来源是用户选择的上下文。
2. 画质门通过后检测 1—4 个对象并输出总数。
3. 若存在 active 基线，则比较每个对象与正、背面基线中的较小合规差异。
4. 页面只显示物体数、疑似变化或无法判断；`no_anomaly_signal` 不生成肯定性卡片。
5. 视觉完成与否都不阻止逐药人工确认。

### 4.2 第二阶段：整组候选分组

1. 检测 1—8 个完整、彼此分离的对象。
2. 候选集合仅取当前任务中 active 且支持闭集比较的外观版本。
3. 每个检测框生成归一化嵌入，与候选的正、背面原型独立比较。
4. 最佳候选必须同时超过接受阈值，并与第二候选满足冻结的最小差距；否则为 `ambiguous` 或 `unassigned`。
5. 不使用计划量作为类别容量或先验，也不以“应该出现的种类”修改结果。
6. UI示例：`根据你的基线，建议分组：药物 A ×1、药物 B ×2；另有 1 个无法分组，请核对。`
7. 用户逐对象确认、改选或标记无法分组；该事实仍只是照片标注，不是服药确认。
8. 清晰对象可部分返回候选，但必须同时显示未分组数量。遮挡、重叠或计数不完整时整张照片回退。

## 5. 端侧实现选择

### 5.1 管线

```text
密文照片与密文基线
  → 原生受控解密
  → manifest/设备/媒体自检
  → 确定性强制回退
  → 传统画质指标
  → detector_quality.tflite 检测、框选和质量信号
  → appearance_embedding.tflite 生成对象嵌入
  → 当前任务闭集距离和拒绝区间
  → 不可变 VisionObservation
  → 清除像素、裁剪、张量和临时嵌入
```

- 检测输入沿用 RGB 640×640 letterbox；外观输入沿用 RGB 224×224。
- CPU、固定 2 线程为首个发布后端；GPU/NNAPI 默认关闭。
- 模型、预处理、阈值、标签、输入输出 schema、数据集和 SHA-256 组成一个只读 manifest。
- 原生模块只向 TypeScript 返回对象框、计数、候选 ID、状态、原因码、版本和耗时。
- JavaScript 不接收照片 Base64、可逆像素缓冲或长期明文路径。

### 5.2 传统视觉的定位

现有 `controlled-contour-v0.1` 可继续用于纯色受控背景的辅助计数和故障对照。它依赖背景均匀和颜色分离，不能用于自然背景类别识别，也不能承担外观基线比较。传统指标仍可承担明暗、模糊和背景噪声门控。

## 6. 类型与 schema v5 提案

TypeScript 冻结于 `src/features/visionInference.ts`：

- `VisionProviderKind`
- `VisionAnalysisInput`
- `VisionProviderCapability`
- `ClosedSetVisionResult`
- `RemoteVisionRequest` / `RemoteVisionResponse`
- `VisionInferenceProvider`

批准接口原样冻结为：

```ts
type VisionProviderKind = "on_device" | "remote_api";

type VisionAnalysisInput = {
  requestId: string;
  photoEvidenceId: string;
  mode: "group" | "per_item";
  candidateMedicationIds: string[];
  appearanceVersionIds: string[];
};

type VisionProviderCapability = {
  available: boolean;
  providerKind: VisionProviderKind;
  modelVersion: string | null;
  supportsBaselineComparison: boolean;
  supportsGroupCandidates: boolean;
};
```

`VisionAnalysisInput` 禁止加入计划数量、实际服用量和库存；药物 ID 与外观版本 ID 由应用层按当前任务生成，Provider 不得扩大候选集合。

未来远程 DTO 冻结为扁平契约：

```ts
type RemoteVisionRequest = {
  schemaVersion: "1";
  requestId: string;
  mode: "group" | "per_item";
  currentImage: EncodedVisionImage;
  references: Array<{
    ephemeralCandidateId: string;
    frontImage: EncodedVisionImage;
    backImage: EncodedVisionImage;
  }>;
};

type RemoteVisionResponse = {
  schemaVersion: "1";
  requestId: string;
  status: "analyzed" | "unable";
  detectedObjectCount?: number;
  objects?: RemoteVisionObject[];
  unableReasonCode?: VisionUnableReasonCode;
  providerModelVersion: string;
  durationMs: number;
};
```

`EncodedVisionImage` 只包含受限 MIME、Base64、解码字节数和 SHA-256，不允许路径、URL、EXIF、药物 ID 或剂量。未来加密信封是独立传输类型，不能替换上述请求字段。

schema v5 采用追加迁移，不删除 v4：

| 表 | 关键字段 | 冻结规则 |
| --- | --- | --- |
| `medication_appearance_versions` | `id, medication_id, version_no, status, reason_code, manifest_version, supersedes_id, created_at_utc` | status 为 `draft/active/manual_only/superseded`；每药最多一个 active |
| `appearance_reference_media` | `appearance_version_id, encrypted_media_id, role` | role 为 `front/back`，复合唯一；只引用加密媒体 |
| `appearance_reference_features` | `appearance_version_id, role, manifest_version, encrypted_feature, created_at_utc` | 特征位于 SQLCipher；manifest 改变后追加新行 |
| `vision_observations` | `id, photo_evidence_id, provider_kind, status, detected_object_count, appearance_status, unable_reason_code, manifest_version, duration_ms, recorded_at_utc` | 不可变；计数属于照片，不是剂量 |
| `vision_object_candidates` | `observation_id, object_index, box_json, status, candidate_medication_id, score_band` | 候选/歧义/未分组互斥；对象索引唯一 |

- v4 `count_observations` 以 `legacy_count_only` 方式投影或迁入新观察，原表保留到回滚验证结束。
- 每药候选数量从对象记录聚合，不另存一份易漂移的汇总事实。
- 任一视觉命令、repository 或表均不得引用消费确认事实或库存流水。

## 7. 强制人工回退

以下任一情况返回 `unable` 或把对象标为未分组：

- Provider、manifest、模型或媒体不可用；哈希、输入输出、NaN、超时或设备检查失败。
- 无 active 基线、基线质量不合格或基线 manifest 不兼容。
- 半片、破损片、透明胶囊或同药新旧外观混用。
- 触边、遮挡、重叠、严重反光、过暗、过曝、模糊或背景噪声。
- 逐药超过 4 个、整组超过 8 个或无对象。
- 两种候选基线过于相似、最佳候选未过阈值或与第二候选差距不足。
- 检测总数与对象记录数量不一致。
- 解密失败、内存压力或处理发生未分类异常。

不得用计划量、药名、处方或上一轮输出解除回退。回退不得阻止照片保存和人工主链。

## 8. 评测与发布门槛

### 8.1 沿用模型卡门槛

- 强制回退违规：0。
- 计数覆盖率总体 ≥80%，核心分层 ≥70%。
- 计数完全一致率总体 ≥95%，核心分层 ≥90%；低估率和高估率各 ≤3%。
- 明显变化被判为内部 `no_anomaly_signal`：点估计 ≤2%，单侧 95% 上界 ≤5%。
- 支持域人工回退率 ≤35%。
- 冷加载 P95 ≤1.5 秒；端到端 P95 ≤3 秒。
- 峰值额外 RSS ≤256 MiB 且不超过设备物理内存 20%。
- 四档真机连续运行 30 次：0 崩溃、0 ANR、0 非有限输出、0 网络请求。

### 8.2 整组候选新增门槛

- 对象候选覆盖率总体 ≥70%，核心分层 ≥60%。
- 已输出候选的错误分配率点估计 ≤2%，单侧 95% 上界 ≤5%；核心分层 ≤5%。
- 已输出候选准确率总体 ≥98%。
- 所有对象均成功分组的支持域照片中，每药候选数量完全一致率总体 ≥90%、核心分层 ≥85%。
- 近似基线、重复外观和候选冲突样例的错误强制分配数为 0。
- 模型输出影响服药事实、剂量或库存的路径为 0。

测试必须覆盖整组/逐药、1/2—4/5—8 个对象、不同光线与背景、相似药物、换批次、遮挡反光、四档 Android 真机及 Provider 关闭。

## 9. 两阶段准入

### Phase V1｜基线与逐药模式

- 完成基线版本、正背面采集、加密存储、质量门和原生 TFLite 窄接口。
- 逐药照片实现计数和基线差异；整组仍只计总数或人工处理。
- 数据、模型、四档真机、隐私清理和人工主链全部通过后，才可申请进入 V2。

### Phase V2｜整组候选分组

- 增加对象嵌入、候选比较、相似基线冲突检测和对象级人工修正。
- 先隐藏运行并记录合成/授权数据指标，达到新增门槛后才显示建议分组。
- 任一药物组合或设备未达门槛时仅关闭整组候选，逐药人工主链继续。

发布状态扩展为：`disabled | count_only | per_item_baseline | closed_set_group_candidates`。后一个状态必须包含前三个状态全部门槛。

## 10. 隐私、安全和未来远程 API

### 10.1 端侧

- 基线与服药照片使用 AES-GCM 逐文件加密；结构化基线、特征和观察位于 SQLCipher。
- 解密、预处理和推理在原生层；异常、超时、退到后台或冷启动时清理临时明文与内存缓冲。
- EXIF位置、设备名称和无关元数据不得进入模型、数据库或日志。
- 基线、特征、模型输出、数据库和密钥排除 Android 自动备份。
- 当前两种 Provider 都不可用；`RemoteVisionProvider` 不持有 endpoint、token、transport 或重试逻辑，且不得调用网络。

### 10.2 未来远程能力的硬前提

远程能力不是当前路线。只有离线方案明确不能达到经签署目标，且产品、医学/药学、隐私、安全和伦理负责人全部批准后，才可单独立项。届时必须：

- 建立新的 ADR、威胁模型、隐私影响评估、地区合规判断、知情同意和退出/删除流程。
- 默认关闭，逐次由用户明确授权；端侧 Provider 仍须可独立使用，远程失败必须回退人工。
- 不发送药名、疾病、处方、计划量、实际服用量、账号标识或稳定设备标识。
- 请求使用一次性随机 `requestId`，服务端按该 ID 做幂等与重放拒绝；传输设计另加端到端混合加密信封、TLS 1.3 和证书固定，但不得改写已批准的远程请求/响应 DTO。
- 服务端只能在受控内存中解密，禁止落盘、训练、遥测、人工查看、第三方转发和跨用途复用。
- 响应必须由严格 Zod schema 拒绝未知字段、非法枚举、非有限数、对象数不一致和未授权候选 ID。
- 服务端响应必须带版本、请求绑定、短期时效和签名；超时、重放、签名错误、候选越界统一返回 `unable`。
- 保存可审计的数据保留期限和删除证明；不得以隐私政策文本代替技术删除。
- 完成照片泄漏、重放、响应篡改、候选注入、模型版本漂移、供应链、降级和断网测试。

即使未来远程实现，结果仍不得自动确认服药、判断剂量或改变库存。

## 11. 当前实施状态

- `OnDeviceVisionProvider.getCapability().available=false`。
- `RemoteVisionProvider.getCapability().available=false`，且不包含网络调用。
- 两者 `analyze` 均返回 `unable/provider_unavailable`。
- 远程响应只提供严格解析契约，不连接任何服务。
- `realPatientDataAllowed=false` 保持不变；模型评测和人类签署前不得把本文描述为现有能力。

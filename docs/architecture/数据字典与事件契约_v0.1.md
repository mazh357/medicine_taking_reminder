# 长期用药管理 APP｜数据字典与事件契约

> 本文把离线 MVP 的产品语义冻结为可实现、可迁移、可测试的数据契约。产品范围和医疗边界以离线 MVP 为最高基线。本文不引入联网、大模型、OCR、医疗建议、照护者、奖励、语音或自动快门。

## 0. 契约结论

1. SQLCipher SQLite 是结构化健康数据的唯一事实源；Zustand、通知系统、页面状态和缓存都不是事实源。
2. `DoseLifecycle`、`ItemConsumptionAssertion`、`PhotoEvidenceState`、`AppearanceAssessment` 四个维度正交保存，任何一个维度不得替代其他维度。
3. 逐药人工确认事实是库存消耗的唯一来源；模型结果、照片、`prepared`、`missed` 和任务级状态均不得直接改变库存。
4. `detected_object_count`、`planned_dose_quantity`、`confirmed_consumption_quantity` 是三个不同概念、不同来源、不同类型的字段，禁止相互赋值或推导。
5. 处方、外观、确认、生命周期和库存纠错保留历史；撤销与修订使用追加事实和反向流水，不覆盖原事实。
6. 当前状态表是可重建投影。投影和事实必须在同一数据库事务中提交，事务失败时全部回滚。
7. 照片内容允许按隐私要求物理销毁；删除成功后保留不可恢复的照片墓碑和追加审计事件。

## 1. 全局存储规范

### 1.1 标识符

- 所有业务主键为应用本机生成的 UUID v4，小写、带连字符，SQLite 类型为 `TEXT`。
- 主键创建后不可修改，不包含患者、药物、时间或设备信息。
- 外键全部启用 `PRAGMA foreign_keys = ON`；健康事实默认 `ON DELETE RESTRICT`，只允许清除全部本机数据时由受控流程统一物理销毁。
- 系统通知 ID、文件路径和模型输出均不能作为业务主键。

### 1.2 时间与时区

| 类型 | 存储格式 | 示例 | 规则 |
| --- | --- | --- | --- |
| 绝对时间 | UTC ISO 8601 `TEXT`，固定毫秒和 `Z` | `2026-08-23T02:30:00.000Z` | 用于创建、拍摄、记录、事件和审计时间 |
| 本地日期 | ISO 8601 `YYYY-MM-DD` | `2026-08-23` | 用于周计划和任务本地归属日 |
| 本地时间 | 24 小时 `HH:mm` | `08:00` | 用户输入的固定计划时间 |
| 时区 | IANA zone ID | `Asia/Shanghai` | 禁止只保存 `GMT+8` 等固定偏移 |
| 偏移快照 | 有符号整数分钟 | `480` | 任务生成时保存，供历史解释，不用于未来重算 |

- `created_at_utc` 表示记录写入时间；业务发生时间使用专门字段，不得混用。
- `regimen` 保存用户的本地计划时间、IANA 时区和两个正整数窗口偏移。`dose_occurrence` 物化 `scheduled_at_utc`、`on_time_until_at_utc`、`record_until_at_utc` 及本地快照，旧任务不得因时区或方案变化被重写。
- 必须满足 `0 < on_time_offset_minutes < record_offset_minutes`，且 `record_until_at_utc` 早于同一方案下一任务的 `scheduled_at_utc`。
- 本地时间落入夏令时不存在区间时，暂停该任务自动派生并要求用户核对；落入重复区间时采用较早偏移并保存偏移快照。系统时区或系统时间变化后，先暂停未来派生，再由提醒重建流程重新物化未到期任务。

### 1.3 十进制定点数量

```text
QuantityText regex := ^(?:0|[1-9][0-9]{0,5})(?:\.[0-9]{0,2}[1-9])?$
Canonical rules:
  - 非负，最大 999999.999
  - 小数最多三位
  - 不允许指数、正负号、前导零、末尾小数零、NaN 或 Infinity
  - "1.500" 必须规范化为 "1.5"；"0.000" 必须规范化为 "0"
```

- 剂量和库存数量在 TypeScript 领域层及 SQLite 中均存为规范化 `TEXT`。
- 运算时转换为千分之一单位的 `bigint`，禁止使用 JavaScript `number` 或 SQLite 浮点聚合。
- 当前单位只允许 `tablet`（片）和 `capsule`（粒）；同一药物的库存单位创建后不可修改，只能新建药物记录。
- `detected_object_count` 为模型观察到的非负整数或 `NULL`，使用 SQLite `INTEGER`；不得写入任何 QuantityText 字段。

### 1.4 通用字段与事实规则

除纯关联表外，业务表至少包含 `id`、`created_at_utc`。可变配置表另含 `updated_at_utc` 和 `row_version INTEGER`；命令更新必须携带预期版本并执行乐观并发校验。

以下记录是不可覆盖事实：处方版本、任务药项快照、生命周期事件、逐药确认事实、撤销事实、库存流水、视觉观察、异常、领域事件和审计事件。修订只能追加新事实。`*_current` 表以及实体上的 `current_*` 字段属于投影，可在事务内更新并能从事实重建。

## 2. 冻结枚举与合法转换

### 2.1 四组正交状态

```ts
export type DoseLifecycle =
  | 'scheduled'
  | 'due'
  | 'prepared'
  | 'taken_confirmed'
  | 'late_taken'
  | 'missed'
  | 'revoked';

export type ItemConsumptionAssertion =
  | 'pending'
  | 'taken_as_planned'
  | 'partially_taken'
  | 'not_taken';

export type PhotoEvidenceState =
  | 'captured'
  | 'skipped_with_reason'
  | 'deleted_tombstone';

export type AppearanceAssessment =
  | {
      status: 'suspected_change';
      reasons: Array<'color' | 'shape' | 'texture' | 'imprint'>;
    }
  | { status: 'unable'; reasonCode: string }
  | { status: 'no_anomaly_signal' };

export type AppearanceAssessmentStatus = AppearanceAssessment['status'];
```

- `DoseLifecycle` 是任务级时间/流程投影，不能用来推断每个药项是否服用。
- `ItemConsumptionAssertion` 是逐药人工声明；任务内每个药项独立保存。
- `PhotoEvidenceState` 只说明照片是否留存或为何未拍，不说明吞服。
- `AppearanceAssessmentStatus` 是端侧模型观察结果，不得触发确认、库存、处方或医疗处置。
- `no_anomaly_signal` 只用于内部诊断和研究指标，禁止生成“正确”“一致”“安全”或任何肯定性用户文案。

### 2.2 `DoseLifecycle` 转换

| 当前 | 允许到达 | 触发条件 |
| --- | --- | --- |
| `scheduled` | `due` | 到达 `scheduled_at_utc` 或前台修复发现已到期 |
| `scheduled` | `revoked` | 任务被受控撤销；不得物理删除 |
| `due` | `prepared` | 整组模式已有覆盖全任务的证据；逐药模式下每个药项均已被照片或跳过原因覆盖 |
| `due` | `missed` | 到达 `record_until_at_utc` 仍有 `pending`，或用户明确全部 `not_taken` |
| `due` | `revoked` | 任务被受控撤销 |
| `prepared` | `taken_confirmed` | 所有药项不再 `pending`，至少一项数量大于零，且首次完整确认不晚于 `on_time_until_at_utc` |
| `prepared` | `late_taken` | 所有药项不再 `pending`，至少一项数量大于零，且首次完整确认晚于正常窗口；若曾生成漏服事实也只能到此状态 |
| `prepared` | `missed` | 到达最晚记录时间仍有 `pending`，或用户明确全部 `not_taken` |
| `prepared` | `revoked` | 所有有效确认被撤销或任务被受控撤销 |
| `taken_confirmed` / `late_taken` | `revoked`、`prepared`、`missed`、二者之一 | 撤销或修订后按剩余有效逐药事实、证据和时间重新派生 |
| `missed` | `late_taken` | 漏服后补录使所有药项不再 `pending` 且至少一项实际数量大于零；原漏服事实保留 |
| `missed` | `revoked` | 任务被受控撤销 |
| `revoked` | `prepared`、`taken_confirmed`、`late_taken`、`missed` | 用户通过修订重新提交事实；必须追加新事件，不得删除撤销事件 |

任务级 `taken_confirmed` / `late_taken` 只表示逐药确认已完成且至少有一项正数量，不表示每个药项都按计划服用；页面和导出必须同时读取逐药状态。若所有药项均为 `not_taken`，任务投影为 `missed`。

### 2.3 `ItemConsumptionAssertion` 转换和数量不变量

`pending` 是没有有效人工确认事实时的投影初值，不写入确认事实表。

| 投影状态 | `confirmed_consumption_quantity` | 规则 |
| --- | --- | --- |
| `pending` | `NULL` | 不扣库存 |
| `taken_as_planned` | 必填且大于零 | 必须等于 `planned_dose_quantity` |
| `partially_taken` | 必填且大于零 | 必须不等于计划量；允许低于或高于计划量，以如实记录为先 |
| `not_taken` | 固定为 `"0"` | 不生成库存消耗流水 |

- `pending` 可经首次确认到任一非 pending 状态。
- 任一非 pending 状态可通过“修订”到另一个非 pending 状态；操作必须同时追加旧事实撤销、新确认事实及库存纠正。
- 任一非 pending 状态可通过“撤销且不替换”回到 `pending` 投影；原事实保留。
- 数量高于计划量时只记录差异和已有的异常类型，不自动解释原因，不提供补救或剂量建议。

### 2.4 照片与视觉状态规则

- 不存在证据记录时不是第四种照片状态。
- 新证据可直接创建为 `captured` 或 `skipped_with_reason`。
- 唯一状态转换为 `captured → deleted_tombstone`。文件和所有派生缩略图确认删除后才提交最终墓碑；跳过记录不可转成伪照片。
- 补拍或重拍创建新的 `photo_evidence`，不覆盖旧记录。
- 每次模型运行创建新的不可变 `vision_observation`；视觉结果之间不存在状态覆盖转换，当前展示取同一照片最新成功提交的观察。
- 半片、破损片、透明胶囊、严重遮挡/重叠、同一种药的新旧外观并用、无可用当前基准、模型错误/超时或设备不支持时，结果必须为 `unable`。整组中存在多种不同计划药物不属于同药外观并用。首版不允许 `size` 原因。

| `dose_item_missed_resolution` | `id`、`missed_event_id`、`assertion_fact_id`、`recorded_at_utc` | 追加式解析关系；`UNIQUE(missed_event_id)`；补录不删除或覆盖漏服事实 |

### 3.3 逐药确认与当前投影

### 3.5 库存与异常

| 表 | 关键字段 | 约束与索引 |
| --- | --- | --- |
| `inventory_ledger` | `id`、`medication_id`、`entry_type`、`quantity_delta`、`unit`、`source_fact_type`、`source_fact_id`、`reverses_entry_id NULL`、`reason_code NULL`、`effective_at_utc`、`recorded_at_utc`、`command_id` | 追加式；delta 是可带负号的规范化定点文本且非零；`UNIQUE(source_fact_type,source_fact_id,entry_type)`；`reverses_entry_id` 唯一；索引 `(medication_id,effective_at_utc)` |
| `exception_record` | `id`、`type`、`occurrence_id NULL`、`occurrence_item_id NULL`、`occurred_at_utc`、`reason_code NULL`、`symptom_text NULL`、`note_text NULL`、`content_version NULL`、`created_at_utc` | type 允许 `late|missed|out_of_stock|suspected_duplicate|uncertain_taken|side_effect|medical_pause`；索引 `(type,occurred_at_utc)` |

库存 `entry_type` 允许：`initial`、`restock`、`consumption`、`reversal`、`manual_adjustment`、`loss`、`damage`。约束如下：

- `initial`、`restock` 和正向 `manual_adjustment` 为正；`consumption`、`loss`、`damage` 为负。
- 每个大于零的有效逐药确认事实生成一条 `consumption`，其绝对值严格等于 `confirmed_consumption_quantity`。
- 撤销一条有消耗的确认事实时，为原流水追加等量相反的 `reversal`，并设置 `reverses_entry_id`。
- 修订为新数量时，不修改旧消耗；先反向旧流水，再按新确认事实追加新消耗。
- 余额由同药物全部有效流水在领域层以 `bigint` 求和；余额允许短时为负并显示“预计库存需核对”，不得丢弃真实确认。

## 4. 事务契约

### 4.1 准备：整组照片

文件系统与数据库不能组成单一 ACID 事务，因此采用“先持久文件、后提交引用”的顺序：

1. 将相机临时文件加密到应用私有目录，完成 GCM 校验和同步落盘。
2. 开启 SQL 事务，创建 active `media_asset`、`photo_evidence(captured)`，并为本任务全部药项创建 `photo_medication_link`。
3. 追加 `PhotoCaptured`、`OccurrencePrepared` 和生命周期事件，更新任务投影为 `prepared`，提交事务。
4. 提交失败时立即删除未引用密文；启动清理器也必须清除无数据库引用的孤儿密文。
5. 数据库提交后才显示“已保存”。视觉分析在提交后异步运行并独立追加，不影响已准备状态。

逐药拍摄复用相同事务，但每个 `photo_evidence` 恰好关联一个任务药项。所有药项必须分别被一张 captured 证据或一条 skipped 证据覆盖后，任务才进入 `prepared`；覆盖未完成时任务保持 `due`，已保存照片不得丢失。

### 4.2 无照片准备

单事务创建 `photo_evidence(skipped_with_reason)`、关联本任务适用药项、追加 `PhotoSkipped` 与 `OccurrencePrepared`，更新任务投影。不得创建 `media_asset` 或伪造拍摄时间。

### 4.3 逐药确认

`ConfirmOccurrenceItems` 必须一次提交用户本次明确选择的药项，未包含的药项保持 pending。事务内依次：

1. 校验幂等键、任务版本、药项归属、已准备证据和数量规则。
2. 为每个选择追加 `consumption_assertion_fact`，更新 `dose_item_current`。
3. 对每个正数量事实追加负向 `inventory_ledger(consumption)`。
4. 按全部当前药项投影和时间窗口重新派生 `DoseLifecycle`；若改变则追加生命周期事件。
5. 追加领域事件、最小研究事件和审计事件，记录 `processed_command` 后提交。

同一命令发生任何错误必须整体回滚，不得出现已确认但未扣库存，或已扣库存但没有确认事实。

### 4.4 修订、撤销与反向流水

- `ReviseItemConfirmation` 在同一事务追加旧事实的 `fact_revocation`、原消耗的 `reversal`、新确认事实和必要的新 `consumption`；二者共享 `revision_group_id`。
- `RevokeItemConfirmation` 只追加撤销和反向流水，当前药项回到 pending，任务按剩余事实和当前时间重新派生。
- 重复撤销返回原结果，不生成第二条反向流水。
- 任务级撤销对所有当前有效药项事实逐一执行上述规则，最后追加 `revoked` 生命周期事件；不得删除照片、异常或历史事实。

### 4.5 漏服与漏服后补录

到达 `record_until_at_utc` 的修复命令必须幂等执行：

1. 为仍为 pending 的每个药项追加唯一 `dose_item_missed_event`。
2. 若任务仍未完整确认，追加 `missed` 生命周期事件和本地研究事件。
3. 用户后续补录时，以 `source='missed_backfill'` 追加确认事实和库存消耗。
4. 追加唯一 `dose_item_missed_resolution` 将原漏服事实连接到补录事实；不得修改或删除漏服事实。
5. 补录完成后任务可投影为 `late_taken`；时间线必须同时显示“曾漏服/漏记”和补录时间。

### 4.6 照片永久删除与墓碑

1. 事务 A 将 `media_asset.deletion_status` 改为 pending，追加 `PhotoDeletionRequested`。
2. 删除密文、缩略图和受控临时文件并验证路径不存在；失败则保持 pending 供前台重试，照片页面不得继续解密展示。
3. 事务 B 清空媒体路径、nonce、tag、哈希和大小，将媒体设为 deleted，将 `photo_evidence` 设为 `deleted_tombstone` 并写入删除时间和 `PhotoDeleted` 事件。
4. 删除不改变任务生命周期、逐药确认、库存或历史视觉观察；用户界面只能显示墓碑，不能显示可恢复缩略图。

## 5. 公开领域接口

所有接口均为设备内 TypeScript port，不得实现 HTTP 或远程 repository。方法返回稳定 `Result<T, DomainError>`；写操作必须在 `UnitOfWork` 中由应用用例编排。

```ts
type UtcInstant = string;
type QuantityText = string;
type IdempotencyKey = string;

type Result<T> =
  | { ok: true; value: T }
  | { ok: false; error: DomainError };

interface DomainError {
  code: DomainErrorCode;
  messageKey: string;
  retryable: boolean;
  details?: Record<string, string | number | boolean>;
}

interface UnitOfWork {
  run<T>(operation: (repos: Repositories) => Promise<Result<T>>): Promise<Result<T>>;
}

interface PrescriptionRepository {
  getVersion(id: string): Promise<PrescriptionVersion | null>;
  appendVersion(command: CreatePrescriptionVersion): Promise<PrescriptionVersion>;
}

interface RegimenRepository {

}

interface DoseRepository {
  getOccurrence(id: string): Promise<DoseOccurrenceView | null>;
  appendLifecycleEvent(event: DoseLifecycleEvent): Promise<void>;
  appendAssertions(facts: ConsumptionAssertionFact[]): Promise<void>;
  appendRevocations(facts: FactRevocation[]): Promise<void>;

}
```

### 6.3 幂等规则

- UI 在一次用户操作开始时生成稳定幂等键；重试、进程恢复和重复点击必须复用该键。
- `processed_command` 的唯一键为 `(command_type,idempotency_key)`。
- 同键、同 payload hash：返回第一次保存的结果引用，不重复执行。
- 同键、不同 payload hash：返回 `IDEMPOTENCY_CONFLICT`。
- 漏服派生键固定为 `missed:{occurrence_id}:{record_until_at_utc}`。
- 单药消耗流水来源唯一键为确认事实 ID；反向流水来源唯一键为被反转流水 ID。
- 照片删除和提醒 reconciliation 必须可安全重入。

## 8. Schema 版本与迁移

### 8.1 v1 基线

- `PRAGMA user_version = 1` 对应本文全部 P0 表、索引、外键、枚举检查和投影。
- `migration_journal` 中版本 1 的 checksum 必须与签名安装包内迁移脚本一致。
- schema 只允许前向迁移；禁止启动时自动降级或由远程配置改变表结构。

### 8.2 迁移步骤

1. 打开 SQLCipher 后校验密钥、`cipher_integrity_check`、外键和当前 user_version。
2. 在应用私有受保护临时区创建本次迁移快照；该快照不是 P1 用户备份，成功或回滚后必须删除。
3. 单事务执行确定性迁移，写 `migration_journal`，运行 `foreign_key_check`、表/索引清单及关键不变量检查。
4. 成功后提交并更新 `user_version`；失败则回滚并进入只读恢复说明，不创建部分新 schema 或明文库。
5. 每个版本测试空库、上一版本真实快照、迁移中断、损坏输入、重复执行和回滚恢复。

### 8.3 兼容规则

- 事件和导出 payload 均带独立 `payload_schema_version`；读取器必须忽略未知可选字段，但拒绝未知必需枚举。
- 迁移不得重算历史模型结果、时区快照、确认数量或库存余额。
- 新枚举值加入前必须先升级读取路径和降级展示；旧版本不允许打开更高 `user_version` 数据库。

## 9. 黄金事件序列

### 9.1 整组照片关联三种药，含部分服用

```text
T1  OccurrenceScheduled(O1; items I1/I2/I3; planned 1/1/0.5)
T2  OccurrenceDue(O1)
T3  PhotoCaptured(P1, mode=group) + links(P1→I1,I2,I3)
T3  OccurrencePrepared(O1)
T4  VisionObservationRecorded(P1, detected_object_count=3,
    appearance_status=no_anomaly_signal)  # 内部值，不显示“通过”
T5  ItemConsumptionAsserted(I1, taken_as_planned, confirmed="1")
T5  ItemConsumptionAsserted(I2, not_taken, confirmed="0")
T5  ItemConsumptionAsserted(I3, partially_taken, confirmed="0.25")
T5  InventoryLedgerAppended(M1, consumption="-1", source=F1)
T5  InventoryLedgerAppended(M3, consumption="-0.25", source=F3)
T5  OccurrenceLifecycleChanged(O1, prepared→taken_confirmed)
```

不为 I2 生成库存流水。P1 的模型计数 3 与任何计划量或实际量都没有自动对应关系。

### 9.2 到期漏服后补录

```text
T1  OccurrencePrepared(O2)
T2  MarkOccurrenceMissed at record_until
T2  DoseItemMissed(I4) + OccurrenceMissed(O2)
T3  ItemConsumptionAsserted(I4, source=missed_backfill,
    assertion=taken_as_planned, confirmed="1", asserted_consumed_at=T3)
T3  InventoryLedgerAppended(M4, consumption="-1", source=F4)
T3  DoseItemMissedResolved(I4.missed_event→F4)
T3  OccurrenceLifecycleChanged(O2, missed→late_taken)
```

时间线同时保留 T2 的漏服事实和 T3 的补录；不得把历史改写为按时服用。

```text
T1  ItemConsumptionAsserted(F5, I5, confirmed="1")
T1  InventoryLedgerAppended(L5, consumption="-1", source=F5)
T2  ItemConsumptionRevoked(F5, revision_group=R1)
```

## 10. 可机器校验的不变量

1. 同一药物最多一个 active 外观版本。
2. 同一方案任务的 `scheduled_at < on_time_until < record_until < next scheduled_at`。
3. 任务药项的三个快照字段不随方案或处方变化。
4. pending 数量为空；not_taken 数量为零；taken_as_planned 数量等于计划；partially_taken 为正且不等于计划。
5. 每个有效正数量确认事实恰有一条等量负向消耗流水；每个被撤销消耗恰有一条等量正向反向流水。
6. 库存单位必须与药物单位一致；余额以定点整数计算。
7. captured 证据必须有 active 密文媒体；skipped 不得有媒体；墓碑不得有可恢复媒体。
8. group 照片关联一个或多个同任务药项；per_item 照片只关联一个同任务药项。
9. 视觉观察只能引用 captured 且未删除时建立的照片；历史照片删除不删除观察记录。
10. 模型结果不得写入逐药确认、计划剂量、实际数量、库存或生命周期事实。
11. 任何任务最终投影都可由生命周期事件、当前有效逐药事实、证据和时间窗口重建。
12. 研究事件和导出默认字段不含照片、药名、疾病、处方文本、症状/备注自由文本或稳定设备标识。

### 13.3 库存预测契约

库存预测是只读派生，不建立新的库存事实：

1. 余额只由同药物 `inventory_ledger.quantity_delta` 以千分之一单位定点求和。
2. 剂量只来自当前生效且 active 的每日固定计划；暂停或没有有效计划时返回“不可计算”。同药多条每日计划按同一时区聚合为每日总计划量；跨时区计划不猜测结果。
3. `fullDoses = floor(max(balance, 0) / dailyDose)`。
4. `estimatedShortageLocalDate = nextFuturePlanLocalDate + fullDoses 天`；当余额不足一次剂量时 `fullDoses=0`，不足日就是下一计划本地日期。
5. 开启补药提醒时，名义触发点为不足日前 `lead_days` 天的计划时区本地 09:00；若对账时已经进入提前窗口，则本次对账把有效触发时间设为当前 UTC，交由系统投影立即安排。
6. `lead_days=NULL` 只关闭补药系统提醒，不关闭库存余额、每日剂量和预计不足日的计算或展示；当前个人测试版应用服务已按此分离计算结果与 `nominal/effective trigger`。
7. `count_observations.detected_object_count`、照片状态和模型结果不得参与余额、每日剂量、`fullDoses`、不足日或提醒触发点计算。

预测本身与提醒投影分离：关闭或取消补药提醒不删除预测偏好之外的药物、计划和库存事实，也不阻止下次按流水重新计算预测。

### 13.4 事项与辅助提醒事务

- 事项创建写 `follow_up_items` 和 `created` 事件；编辑仅允许 pending，采用 `row_version` 乐观并发，并追加完整新快照；完成或取消追加事件和时间戳。任何路径均不物理删除事项或旧事件。
- 新建或编辑 pending 事项时创建/更新 `follow_up_due` 意图；配置提前天数时另建 `follow_up_advance` 意图。完成、取消或移除提前设置时，数据库意图进入取消流程。
- 系统通知 ID 只保存在 projection。调度、重启、权限恢复和前台对账均从 intent 重建 projection；不得从系统通知反推事项或库存事实。
- 取消系统通知失败时，保留原 `system_notification_id`，projection 保持 `cancel_pending` 并记录失败，后续对账重试；不能因取消失败删除 intent、创建重复 ID 或声称已经取消。

### 13.5 全部清除

“全部清除”是独立于单项墓碑和事项取消的设备级销毁流程：先停止业务访问并取消本应用通知，再删除加密媒体、解密缓存及媒体密钥；随后写入持久清除标记、关闭 SQLCipher，依次删除并确认不存在数据库 `-wal`、`-shm` 和主文件；数据库文件全部删除后才销毁数据库密钥并清除 pending 标记。下一次初始化才允许生成新密钥并按空库路径创建 schema v4。任一步失败均进入恢复状态；下次启动发现 pending 标记时必须先继续删除数据库文件与密钥，不得用新空库遮盖仍存在的旧密文或声称清除完成。
